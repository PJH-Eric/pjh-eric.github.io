# 全遊戲整合規劃書（單一專案・共用伺服器・微前端）

> 撰寫日期：2026-10-28
> 範圍：`C:\Eric\AI Agent` 下 18 款遊戲＋`game-lobby`＋`pjh-eric.github.io`
> 本文件只做規劃，不含實作。

---

**目標**

把 18 款遊戲搬進同一個 monorepo（暫名 `pjh-games`），讓多語系、GA4／SEO、伺服器網址設定、自繪 UI、WebSocket 連線層、房間邏輯都只維護一份。前端用「微前端」：大廳當 shell，每款遊戲獨立建置、按路徑載入。後端分兩階段：

- **階段 A（3～4 週）**：建立 monorepo、共用前端套件、微前端。這段期間後端維持現狀，線上服務不中斷。
- **階段 B（3～4 週，必做）**：**共用伺服器**。一個 `game-server` 統一處理連線、大廳、房間、觀戰、聊天、邀請、斷線重連，每款遊戲只提供規則外掛；Render 收斂成一個 service、本機只開一個 port。

第一個原則是**玩家看到的網址不變**，SEO 和已分享出去的邀請連結都不能斷。

## 二、目標架構

```
pjh-games/                       ← 新 monorepo（npm workspaces，維持零外部依賴的習慣）
├─ package.json                  ← workspaces、build-all、verify-all
├─ games.json                    ← 從 game-lobby/config/games.json 升級，全專案唯一的遊戲清單
├─ packages/
│  ├─ web-core/                  ← analytics.js、i18n.js、config.js、server-wakeup.js（喚醒動畫）
│  ├─ ui-kit/                    ← 自繪按鈕／選單／開關／輸入框／捲軸／縮放鈕（合併五種寫法）
│  ├─ seo/                       ← inject-seo.js、inject-server-url.js、sitemap 產生
│  ├─ net-server/                ← WebSocket 伺服器（以 lib/ws.js 200 行版為基礎）、心跳、延遲
│  ├─ net-client/                ← 瀏覽器端連線、重連、ping
│  └─ rooms-core/                ← 【階段 B】房間生命週期核心
├─ apps/
│  ├─ lobby/                     ← 原 game-lobby，當微前端 shell
│  ├─ site/                      ← 原 pjh-eric.github.io（robots.txt、sitemap、Search Console）
│  └─ game-server/               ← 【階段 B】統一後端
├─ games/
│  ├─ amaze-go/ … whack-a-mole/  ← 18 款，維持各自的 public/、server.js、tests/
└─ scripts/
   ├─ sync-shared.js             ← 把 packages/* 複製進各款 public/js/shared/（建置時）
   ├─ build-all.js               ← 依 games.json 逐款建置、注入、輸出到 site-dist/
   └─ verify-all.js              ← 逐款跑 npm run verify
```

**微前端的做法：以路徑切分，建置時整合**

- 每款遊戲是獨立的靜態網頁，部署在 `https://pjh-eric.github.io/<遊戲 id>/`，**和現在的網址一模一樣**。
- 共用套件在建置時複製進各款的 `public/js/shared/`，純 JS 的遊戲照舊用 `<script>` 載入，不需要改成打包工具。
- 不使用 Module Federation 這類執行期整合：遊戲大多是純 JS，用執行期整合要付出的複雜度大於好處，而且 3D 遊戲的大包本來就該和大廳分開載入。

**部署**

> 後端採「模組化單體」：一個程序、一份部署，但每款遊戲是獨立的外掛模組，程式碼邊界和微服務一樣清楚，日後要把某款拆出去只要改 `GAMES` 環境變數。

- 前端：只用一個 GitHub Pages，從 `pjh-eric.github.io` 根網域 repo 輸出整個 `site-dist/`。子路徑 `/fruit-link/` 等對應原本的 project page 網址，所以網址不變。
- 後端：
  - 階段 A：各款沿用現有的 Render service，不動。
  - 階段 B：全部切換到同一個 `game-server` service，WebSocket 依路徑 `/ws/<遊戲 id>` 分流。所有遊戲的 `GAME_SERVER_URL` 都指向同一台。舊的 18 個 service 確認無流量後停用。

- **階段 B**：同時開多款遊戲的房間做壓力測試，確認在 Render 免費方案的記憶體限制內；冷啟動喚醒動畫要正常顯示。

## 八、風險與待決事項

1. **GitHub Pages 網址繼承**（最關鍵）：要先在階段 0 驗證。如果不通，備案是各款保留自己的 repo 和 Pages，monorepo 只發布共用套件（由 `sync-shared` 推送到各 repo）。這樣仍然算「共用前端」，只是部署沒有合一。共用伺服器不受影響，各 repo 的前端一樣連到同一台 `game-server`。
2. **Render 免費方案限制**：合併成單一服務後，所有遊戲共用一份記憶體和 CPU 額度，也共用同一次冷啟動。好處是任何一款喚醒伺服器，其他遊戲就不用再等；風險是即時物理類可能拖慢其他遊戲，要靠第 24 步的負載測試確認。
3. **共用伺服器是單一故障點**：一個外掛丟出例外不能拖垮整台。`game-server` 要替每個外掛包錯誤處理，出錯只關閉該房間並記錄；部署前要跑全部 18 款的線上測試。
4. **既有的公開 repo**：封存還是刪除、要不要在 README 放轉址說明，需要你決定。
5. **ui-kit 統一的程度**：只統一元件行為、保留各款配色（建議），或連視覺也統一。後者會多 1～2 週。
6. **不在這次範圍內**：`SerilogLogViewer`、`kindergarten-management-system`、`日月光GIS`、`skills` 這幾個非遊戲資料夾。
